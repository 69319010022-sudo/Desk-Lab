# DeskLab API - RLS Audit (Bruno collection)

ทดสอบ Supabase REST API (PostgREST) ของโปรเจกต์ DeskLab โดยตรง ข้าม Next.js
app ไปเลย เพื่อยืนยันว่า Row Level Security (RLS) ที่ตั้งไว้ทำงานถูกต้องจริง
ที่ระดับ API ไม่ใช่แค่ "ผ่านเพราะ UI บังคับ query ให้ถูกต้องอยู่แล้ว"

ทุก assertion ในคอลเลกชันนี้ **ตรวจสอบจริงกับโปรเจกต์ Supabase จริง
(wrokdxuxazwzpttghrko) แล้ว** ไม่ได้เดา status code เอาเอง

## วิธีใช้

1. เปิดโฟลเดอร์ `bruno/` นี้ใน Bruno app (File → Open Collection)
2. เลือก environment "Local" (มุมขวาบน)
3. รันตามลำดับโฟลเดอร์ 00 → 06 (จากบนลงล่าง) รอบแรกครั้งเดียว:
   - **00 - Setup**: สร้างบัญชีทดสอบ 2 บัญชี (`bruno.testa@desklab.test`,
     `bruno.testb@desklab.test`) — รันซ้ำได้ปลอดภัย ครั้งที่ 2 เป็นต้นไปจะ
     ได้ 422 "already registered" ซึ่งถือว่าผ่านปกติ
   - **01 - Auth**: ล็อกอินทั้งสองบัญชี ระบบจะดึง access token/user id
     เก็บไว้ใน environment ให้อัตโนมัติ (ต้องรันก่อนทุกโฟลเดอร์ถัดไป)
   - **02 - 03**: เช็คสิทธิ์ของผู้ใช้ที่ยังไม่ล็อกอิน (anon)
   - **04**: เช็คว่า Test User A เห็น/แก้ได้เฉพาะข้อมูลของตัวเอง (มี fixture
     สร้างที่อยู่ + ออเดอร์ให้ใช้ในขั้นถัดไปด้วย)
   - **05**: เช็คว่า Test User A แตะข้อมูลของ Test User B ไม่ได้เลย
   - **06**: เช็คกฎทางธุรกิจเฉพาะ (ลูกค้าเปลี่ยนสถานะออเดอร์เป็น "paid" เอง
     ไม่ได้, เขียน payments เองไม่ได้)

หลังจากนั้นจะรันซ้ำแค่บางโฟลเดอร์ก็ได้ (เช่นหลังแก้ RLS policy ใหม่) แค่ต้อง
รัน **01 - Auth** ใหม่ก่อนเสมอถ้า access token หมดอายุ (ปกติ ~1 ชั่วโมง)

## บัญชีทดสอบ

ใช้อีเมล/รหัสผ่านสมมติที่ตั้งไว้ตรงๆ ใน environment (`bruno.testa@desklab.test`
/ `BrunoTest123!` และ `bruno.testb@desklab.test` / อันเดียวกัน) — เป็นบัญชี
ทดสอบล้วนๆ ไม่ใช่ข้อมูลลูกค้าจริง ปลอดภัยที่จะ commit เก็บไว้ในโปรเจกต์

`anon_key` ใน environment คือ public anon key ตัวเดียวกับที่แอปใช้ฝั่ง client
อยู่แล้ว (`NEXT_PUBLIC_SUPABASE_ANON_KEY`) ปลอดภัยที่จะ commit เช่นกัน —
**ไม่มี service role key อยู่ในคอลเลกชันนี้เลย** เพราะจุดประสงค์คือทดสอบ RLS
ในมุมมองของผู้ใช้จริง (anon/authenticated) ถ้าใช้ service role จะข้าม RLS
ไปหมด ทดสอบไม่ได้ผลอะไร

## สรุปสิ่งที่ยืนยันแล้วว่าทำงานถูกต้อง (ผลจริงจากการรันตรวจสอบ)

- ตารางแคตตาล็อกสาธารณะ (categories/products/product_images/reviews):
  anon อ่านได้ (200), เขียนไม่ได้แม้แต่คนเดียว (401)
- ตารางข้อมูลส่วนตัวทั้งหมด (users/addresses/orders/payments/carts/
  order_items/activity_logs): anon เห็นเป็นอาร์เรย์ว่างเสมอ (200 + `[]`
  ไม่ใช่ error)
- ผู้ใช้ที่ล็อกอินแล้วเห็น/แก้ได้เฉพาะแถวของตัวเอง ข้าม user อื่นไม่ได้ ทั้ง
  ตอน SELECT (ได้ `[]`) และ UPDATE (แก้ได้ 0 แถว)
- INSERT ข้าม user (เช่นปลอม activity log เป็นอีกคน) โดน block จริงด้วย 403
- ลูกค้าเปลี่ยนสถานะออเดอร์ตัวเองจาก pending → paid เอง **ไม่ได้** (403)
  แต่ pending → cancelled ทำได้ปกติ (200) — ตรงตามที่ตั้งใจออกแบบไว้
- เขียน payments โดยตรงด้วย token ของลูกค้าเอง (แม้แต่ออเดอร์ของตัวเอง) **
  ไม่ได้เลย** (403) — ต้องผ่าน service role เท่านั้น ตรงตามที่ตั้งใจไว้
