# สคริปต์รีวิวโปรเจกต์ DeskLab สำหรับทีมเทคนิค (พูดได้ใน 3-5 นาที)

*ครอบคลุม: เก็บข้อมูลยังไง / กระบวนการทำงาน (Process) / Tech Stack และเหตุผลที่เลือก / เทียบกับตัวเลือกอื่น*

## เกริ่นนำ (30 วินาที)

DeskLab เป็นเว็บอีคอมเมิร์ซขายของแต่งโต๊ะทำงาน/คอมพิวเตอร์ มีทั้งฝั่งหน้าร้านลูกค้า (สมัครสมาชิก เลือกสินค้า ตะกร้า checkout จ่ายเงินจริง) และฝั่ง Admin Dashboard (จัดการสินค้า จัดการออเดอร์ ดูยอดขาย) ตอนนี้ deploy ขึ้น production จริงแล้วที่ `desk-lab-omega.vercel.app` และมีแผนต่อยอดเป็นเฟส 2 คือโปรแกรมจำลองการจัดโต๊ะ

## Tech Stack ที่ใช้ และทำไมถึงเลือก (1.5-2 นาที)

**Frontend + Backend: Next.js (App Router) + React + TypeScript**
เลือกตัวนี้เพราะ Next.js ให้เขียน frontend กับ backend อยู่ในโปรเจกต์เดียวกันได้เลยผ่าน "Server Actions" — ไม่ต้องแยกทำ API server ต่างหาก โค้ดที่ดึงข้อมูลจาก database ก็รันฝั่ง server ได้ตรงๆ ปลอดภัยกว่าไปเรียกตรงจาก browser แล้ว TypeScript ช่วยจับ error ตอนเขียนโค้ดก่อนที่จะไปพังตอนรันจริง

ถ้าจะใช้ตัวอื่นแทน: **Remix** ทำงานคล้ายกันมากแต่ community/ตัวอย่างโค้ดน้อยกว่า, **SvelteKit** เขียนโค้ดสั้นกว่าและเว็บโหลดเร็วกว่านิดหน่อย แต่ต้องเรียนภาษา Svelte ใหม่และหา library เสริมยากกว่า React ที่มีคนใช้เยอะที่สุดในตลาด, หรือถ้าไม่ใช้ framework เลยก็ต้องแยกทำ React (frontend) + Express/Node (backend) เอง ซึ่งเขียนโค้ดเชื่อมสองฝั่งเยอะกว่าและดูแลยากกว่า

**Styling: Tailwind CSS**
เขียน style ตรงใน component เลย ไม่ต้องสลับไปแก้ไฟล์ CSS แยก ทำงานเร็วกว่าและไฟล์ CSS สุดท้ายที่ส่งให้ผู้ใช้เล็กเพราะตัด class ที่ไม่ได้ใช้ทิ้งอัตโนมัติ ทางเลือกอื่นเช่น CSS Modules หรือ styled-components ก็ทำได้เหมือนกันแต่เขียนช้ากว่าเพราะต้องตั้งชื่อ class เอง

**Database + Authentication: Supabase (บน Postgres)**
เลือกเพราะได้ 3 อย่างในตัวเดียว: ฐานข้อมูล SQL (Postgres), ระบบสมัครสมาชิก/ล็อกอิน, และ Row Level Security ที่ล็อกสิทธิ์เข้าถึงข้อมูลได้ละเอียดถึงระดับแถว โดยไม่ต้องเขียน backend server แยกมาตรวจสิทธิ์เอง ข้อมูลร้านค้าแบบนี้ (ลูกค้า-ออเดอร์-สินค้า) มีความสัมพันธ์ระหว่างตารางชัดเจน ใช้ฐานข้อมูลเชิงสัมพันธ์แบบ SQL จะออกแบบและ query ตรงไปตรงมากว่า NoSQL อย่าง Firebase/Firestore มาก

ทางเลือกอื่น: **Firebase** เป็น NoSQL ถ้าข้อมูลมีความสัมพันธ์ซับซ้อนแบบนี้จะออกแบบยากกว่า, **PlanetScale** (MySQL) เร็วและ scale ง่ายแต่ไม่มีระบบสิทธิ์ระดับแถวในตัว ต้องเขียน auth layer เอง, หรือ self-host Postgres เองก็ทำได้แต่ต้องดูแล server/security เอง เสียเวลากว่ามาก

**Hosting: Vercel**
เลือกเพราะเป็นบริษัทเดียวกับผู้สร้าง Next.js รองรับฟีเจอร์ทุกอย่างของ Next.js เต็มรูปแบบ และเชื่อม GitHub แล้ว deploy อัตโนมัติทุกครั้งที่ push โค้ด ฟรีสำหรับเริ่มต้น ทางเลือกอื่นคือ Netlify (รองรับ Next.js ได้แต่ไม่ราบรื่นเท่า) หรือ Railway/Render ซึ่งเหมาะกับงานที่แยก backend server ต่างหากมากกว่า

**Payment: Opn Payments (เดิมชื่อ Omise)**
เป็น payment gateway สัญชาติไทย รองรับพร้อมเพย์ บัตรเครดิต/เดบิต และเก็บเงินปลายทางในตัวเดียว มีโหมด sandbox ทดสอบฟรีก่อนเปิดใช้จริง ทางเลือกอื่นอย่าง Stripe ไม่รองรับพร้อมเพย์ธนาคารไทยโดยตรง ต้องต่อผ่านตัวกลางเพิ่ม

## เก็บข้อมูลยังไง (1 นาที)

ข้อมูลหลักทั้งหมดเก็บใน **Supabase (Postgres)** แบ่งเป็น 12 ตาราง เช่น users, products, categories, orders, order_items, cart_items, payments, activity_logs — ออกแบบความสัมพันธ์ระหว่างตารางไว้ชัดเจน (เช่น 1 ออเดอร์มีได้หลายสินค้า ผูกกับที่อยู่จัดส่งและลูกค้าคนเดียว)

ทุกตารางเปิด **Row Level Security** ไว้ — กติกาคือลูกค้าเห็น/แก้ได้เฉพาะข้อมูลของตัวเอง (ออเดอร์ ตะกร้า ที่อยู่ของตัวเอง) ส่วนข้อมูลสินค้า/หมวดหมู่เปิดให้ทุกคนอ่านได้แต่แก้ไม่ได้ ยกเว้นผ่านสิทธิ์แอดมินเท่านั้น การชำระเงินก็ล็อกไว้ให้แก้ได้ผ่านระบบฝั่งเซิร์ฟเวอร์เท่านั้น กันไม่ให้ลูกค้าปลอมสถานะจ่ายเงินเองได้

รูปสินค้าเก็บเป็นไฟล์ static ในตัวเว็บเอง ไม่ได้ใช้ Supabase Storage แยก ส่วนโค้ดทั้งหมดเก็บบน GitHub และมี CI ตรวจ type/lint/test/build อัตโนมัติทุกครั้งที่ push นอกจากนี้ยังมีการเตรียมระบบฐานข้อมูลสำรอง (SQLite/MySQL/MongoDB) ไว้เป็นโครงตารางเผื่ออนาคตถ้าต้องการทำ failover แต่ยังไม่ได้เชื่อมทำงานจริง

## กระบวนการทำงาน / Process (30-45 วินาที)

ทำงานแบบทีละขั้นตอนเสมอ ไม่ทำหลายอย่างพร้อมกันในคราวเดียว: ก่อนเริ่มงานใหม่ทุกครั้งจะเขียนแผนไว้ในเอกสารกลางของโปรเจกต์ก่อน ทำเสร็จทีละส่วน แล้วทดสอบจริงก่อนส่งมอบทุกครั้ง — ทั้งตรวจ type ตรวจ lint สั่ง build จริง และเปิดเบราว์เซอร์ทดสอบพฤติกรรมจริงทั้งหน้าจอปกติและหน้าจอมือถือ/แท็บเล็ต จากนั้นค่อย commit/push แยกเป็นหน่วยงานย่อยที่ชัดเจน และปิดท้ายด้วยการอัปเดตเอกสารแผนงานให้ตรงกับสถานะจริง เพื่อให้กลับมาทำงานต่อได้ทุกครั้งโดยไม่หลงทาง

---

## สรุปทำไมถึงเลือกชุดนี้ (15-30 วินาที)

ทั้งชุดใช้ TypeScript ตัวเดียวกันตั้งแต่ frontend ถึง database layer ลดความคลาดเคลื่อนของชนิดข้อมูล, ทุกตัวมี free tier เริ่มต้นไม่มีค่าใช้จ่าย เหมาะกับโปรเจกต์ขนาดเริ่มต้น-กลางที่ไม่มีทีม infra คอยดูแลเซิร์ฟเวอร์เอง, และเป็นเครื่องมือที่ community ใหญ่ หาเอกสาร/ตัวอย่างแก้ปัญหาได้ง่ายเวลาติดปัญหา
